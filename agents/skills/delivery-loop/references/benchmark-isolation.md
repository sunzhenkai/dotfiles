# Benchmark Isolation

benchmark 只用于评估 skill 或 agent 的未被提示能力，不用于普通交付。用户必须显式写出 `benchmark:`、`盲测:` 或 `回归复跑:`；默认一律 normal。

## 实现者输入

只允许：

- 目标 / 样例原文，逐字保留
- 工作目录与写入范围
- 语言、依赖、运行环境约束
- 本地启动要求
- 时间预算
- “不 commit / 不 push / 不部署 / 不外发”约束
- 交付要求：可运行、有测试、有说明、留证据

禁止：

- 质量画像
- 角色底线
- 评分 rubric
- 期望页面 / 功能清单
- 审阅意见
- 历史失败细节
- 事后补充的隐藏提示

## 审阅者输入

审阅者持有：

- 质量画像
- taskflow 的 acceptance rubric（五维、UI/UX 六子项与通过线的唯一真相源）
- 已知生产性降级表

审阅者与实现者不共享这些内容。

## 首次盲测与复跑

首次盲测只需要记录并哈希目标原文、运行约束和评审专用画像，不要求跑两遍。输出报告标明 `first-run`。

显式 `回归复跑` 或修复后复跑才比较两轮结果；两轮必须使用同一份目标原文、运行约束和评审专用画像。任何一项变化即开启新 benchmark，不得与旧结果比较。

## 复跑

- 使用同一份目标原文、运行约束和评审专用画像。
- 不因首轮失败追加提示词。
- 换提示后就是新 benchmark，不得与旧结果比较。
- 记录 prompt 哈希或原文快照，证明可比性；首次盲测同样要记录，作为未来复跑基线。

## 归因

- implementation bug：目标语义清楚，实现错误。
- skill gap：目标语义清楚，但流程 / 指引导致实现者系统性地漏质量面。
- acceptance gap：评审标准漏项或不可检查。

只有 skill gap 才修改 skill，并走 skill-upgrader patch。

## 输出

benchmark 报告必须区分：

- 实现产物质量
- skill 流程质量
- 评审 / rubric 质量
- 修复后复跑结果

不得把实现者复述提示词的能力当作 skill 改进效果。
