# 实现者隔离

复杂交付容易因为「实现者早知道验收期望」而得出虚高结论。派发实现时按本文件隔离输入，让验证测的是流程能力，不是复述能力。

## 实现者只收到

- 需求或样例原文（保持原样，不改写、不补充期望）。
- 工作目录、允许写入的范围与不得提交/不得外发的约束。
- 运行约束：语言与依赖边界、本地启动要求、时间预算。
- 交付要求：可运行、有测试、有说明、留证据。

## 实现者不收到

- 质量画像、角色底线清单。
- 验收 rubric、评分维度与通过线。
- 期望的页面清单、功能清单或「必须包含」的隐藏清单。
- 审阅者的具体意见与历史失败细节。

需要实现者知道的信息，必须已经写在需求原文或运行约束里；写不进去的期望，说明画像或需求还没定清，回去补，不靠私聊提示词传递。

## 派发方式

1. 记录本次派发的样例/需求原文，作为可复跑的输入。
2. 由审阅者持有画像与 rubric；实现者与审阅者不共享这两份内容。
3. 同一输入需要复跑时，用同一份原文，不追加事后提示；否则结果不可比。
4. 实现者产出直接进交付仓与证据目录，编排者只做审计与应用，不改写实现者结论。

## 并行时

- 多个实现者并行时，每个只拿自己那一块的原文与约束，不给别人的期望。
- 子代理产出按 [delivery-quality-loop.md](delivery-quality-loop.md) 归因与复验。

## 边界

- 隔离的是「验收期望」，不是必要上下文；构建方式、环境、依赖这些属于运行约束，要照常给。
- 隔离不降低实现要求：画像与 rubric 仍然生效，只是由审阅者而非实现者持有。
