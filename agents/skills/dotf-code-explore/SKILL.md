# 代码探索

使用此技能对一个或多个仓库建立可靠且有边界的理解。将**理解**与**实现**分开：先检查并解释；探索期间不得修改源代码、配置、基础设施或外部系统。

## 操作假设

将以下内容视为可配置的占位符，而不是固定路径：

- `REPO_ROOT`：包含一个或多个仓库的目录。
- `KNOWLEDGE_ROOT`：持久化文档、架构笔记、规范或索引所在位置。
- `PROJECT_ROOT`：可选目录，其中每个仓库对应一个 profile/card。

如果工作区使用了不同的名称，应从仓库根目录中发现这些名称，并简要说明映射关系。绝不要臆造组织特定的默认值。

## 阶段选择

支持以下阶段。如果用户没有指定阶段，则推断最有把握的阶段，并用一行说明该推断。

| 阶段 | 用途 | 默认写入行为 |
|---|---|---|
| `ask` | 优先基于现有知识回答聚焦的行为、术语或规则问题。 | 只读 |
| `explore` | 追踪实现路径、依赖关系、数据流或变更影响。 | 只读 |
| `archive` | 将经过验证的发现整理为持久化且相互关联的文档。 | 仅在明确请求后写入 |
| `ingest` | 在保留来源和不确定性的前提下，存储用户提供的知识。 | 仅在明确请求后写入 |
| `project` | 创建或查询紧凑的仓库 profile，以便快速了解仓库。 | 仅在明确请求后写入 |

如果请求在两个阶段之间存在歧义，应提供两种解释，而不是悄悄执行写入操作。如果用户要求实现或编辑代码，则停在探索边界，并交接给仓库的实现工作流。

## 证据与安全规则

1. **在检查源代码前优先使用已有知识。** 从索引、规范、架构笔记和项目 profile 开始。
2. **采用渐进式披露。** 只读取回答问题所需的证据；默认不要扫描整个工作区。
3. **让结论有证据支撑。** 引用仓库相对路径、符号、配置键、接口或明确的调用关系。
4. **保持探索只读。** 不要编辑文件、创建提交、切换分支、安装依赖、运行破坏性命令或调用具备写入能力的 API。
5. **外部变更必须经过确认。** 任何数据库、云服务、集群、部署、配置服务或工单/文档变更，都需要单独且明确的确认门槛。
6. **隐去机密信息。** 绝不要输出凭据、令牌、私钥、个人联系方式、内部主机名或敏感载荷。将它们替换为 `<REDACTED>`，仅保留必要的结构。
7. **不要过度断言。** 区分已观察到的事实、强推断、假设和未知信息。
8. **保护无关工作。** 不要重新格式化、重新生成或“清理”请求文档范围之外的文件。

## 渐进式加载协议

按以下层级顺序使用，并在问题得到回答后立即停止：

- **L0 — 路由：** 仓库索引、工作区 README、文档索引或项目卡片索引。
- **L1 — 概览：** 仓库 README、模块地图、包清单、服务目录、符号索引或顶层规范。
- **L2 — 细节：** 最小的相关设计笔记、配置文档、关系图、测试或源代码文件集合。
- **L3 — 证据追踪：** 针对符号、调用链、数据流或影响分析的定向源代码检查。

除非有明确且具体的理由，否则 L0–L2 合计预加载文件数保持在**六个或更少**；如超过，应在报告中说明例外原因。在进行广泛内容搜索前，先使用索引或符号搜索。除非与问题直接相关，否则避免读取生成文件、第三方 vendored 依赖、构建产物和无关历史记录。

### 证据层级

在注意冲突的同时，按以下顺序优先采用证据：

1. 当前源代码和可执行测试。
2. 版本化的规范和设计文档。
3. 仓库文档和配置 schema。
4. 持久化项目 profile 和架构笔记。
5. 用户提供的陈述和历史笔记。
6. 仅基于命名或惯例的猜测。

当来源相互矛盾时，应报告冲突，并解释对于当前问题哪个来源更具权威性。

## 阶段：`ask`

用于回答聚焦问题，例如“这个选项是什么？”“这条规则在哪里定义？”或“这个组件负责什么？”。

### 流程

1. 解析主题、仓库、时间范围以及所需的详细程度。
2. 加载 L0–L2 知识，并在打开源代码前通过索引进行路由。
3. 如果已有知识足够，直接回答。
4. 如果需要追踪源代码，建议使用 `explore`；只有当用户明确希望快速回答且证据范围可以受限时，才执行小范围的有边界查询。
5. 说明置信度和证据缺口。

### 输出

```markdown
## 答案
<用一到三句话给出结论>

## 证据
- `<仓库相对路径>` — `<章节、符号或关系>`
- `<仓库相对路径>` — `<支持性要点>`

### 摘要与置信度
- **摘要：** <简短重述>
- **置信度：** high | medium | low — <原因>
```

保持回答简短。只有在升级处理或记录文档有帮助时，才添加下一步建议。

## 阶段：`explore`

用于调用链追踪、仓库导览、依赖分析、数据流分析、回归风险或变更影响评估。探索不是实现。

### 流程

1. **界定任务。** 记录问题、范围、目标行为和成功条件。
2. **识别仓库。** 根据明确路径、仓库名称或工作区索引解析出唯一仓库。如果有多个候选项匹配，应列出它们，不要自行猜测。
3. **加载上下文。** 读取相关的 L0–L2 材料，然后识别可能的入口点、边界和输出。
4. **绘制路径。** 沿着符号和接口追踪最小且有用的链路：入口点 → 校验/分发 → 核心逻辑 → 副作用/输出。
5. **检查支持性证据。** 检查相关测试、配置、schema、错误处理和相邻调用方。
6. **评估影响。** 区分直接调用方、间接消费者、配置或数据契约依赖，以及可能的回归面。
7. **记录不确定性。** 列出未经验证的假设、动态/基于反射的边、生成代码和缺失的测试。
8. **在有用的边界停止。** 不要仅仅为了让地图看起来完整，就继续进入无关模块。

### 仓库检查顺序

根据仓库使用的语言和布局进行调整，默认采用以下顺序：

1. 顶层 README 以及贡献/开发者文档。
2. 构建或包清单，以及工作区/模块定义。
3. 目录/模块地图和服务边界。
4. 已命名的入口点、路由、命令、处理器或公共 API。
5. 核心符号及其直接调用方/被调用方。
6. 约束行为的测试、schema、配置和部署元数据。

### 搜索规范

- 在搜索通用术语前，先搜索精确符号、路由名称、配置键、错误码和接口名称。
- 在可用时，优先使用结构化或理解符号的搜索。
- 通过仓库、目录、文件类型和明确的搜索模式限制广泛搜索。
- 总结发现，不要粘贴大段源代码。
- 只有当问题涉及意图、回归、归属或时间点时，才检查历史记录；历史查询应保持范围狭窄。

### 有边界的委派

当有只读子代理或并行工作器可用时，只委派相互独立且范围明确的侦察任务：

- `repo-scout`：阅读概览文档并定位可能的入口点。
- `code-tracer`：从已知入口点追踪一条指定路径。
- `impact-scout`：识别调用方、消费者、测试和配置依赖。

为每个工作器指定一个仓库和一个问题。要求提供紧凑的简报，而不是源代码转储：

```markdown
## ExplorationBrief
- repository: `<相对路径>`
- entries: [`<路径:符号> — <职责>`]
- call_chain: [`A -> B -> C`]
- findings: [`<路径> — <有证据支撑的要点>`]
- risks: [`<风险或未发现风险>`]
- unknowns: [`<未经验证的要点>`]
- files_read: <数量>
```

默认最多使用两个并行工作器。不要委派一个在本地取得任何有用进展之前就必须等待其结果的任务。如果没有子代理能力，则在本地应用相同的范围和输出约束。

### 输出：五部分探索报告

```markdown
## 任务理解
- **问题：** <调查了什么>
- **范围：** <包含和排除的仓库/模块/文件>

## 代码地图
1. `<路径:符号>` — <作用>
2. `<路径:符号>` — <作用>
3. `<路径:符号>` — <作用>

**调用/数据路径：** `<A> -> <B> -> <C>`

## 发现与风险
- <有证据支撑的发现>
- <直接或间接影响>
- <风险、缺失测试或不确定性>

## 选项或下一步
- <只读后续操作、验证或实现交接>

## 证据与审计
- `<路径>` — <相关章节/符号及其重要性>
- 读取文件数：<数量>；使用工作器数：<数量或无>
- 写入/外部变更：无

### 摘要与置信度
- **摘要：** <用一到两句话回答>
- **置信度：** high | medium | low — <依据和剩余缺口>
```

当某个类别没有结果时，明确使用“未发现”。不要因为某个假设符合命名方式，就将其当作事实。

## 阶段：`archive`

仅在用户要求将探索结果保留为持久化知识时使用。

### 流程

1. 确定 `KNOWLEDGE_ROOT` 下的规范文档位置。
2. 检查索引和附近文档，确认是否已有事实来源。
3. 决定是更新、链接还是创建；避免复制同一规则的重复内容。
4. 编写简洁文档，包含范围、结论、证据链接、置信度和开放问题。
5. 只更新使该文档可被发现所必需的索引。
6. 报告所有已修改的文件和任何未解决的冲突。

建议的文档元数据：

```yaml
---
title: <简短主题>
type: code-map | architecture | behavior | decision | investigation
status: draft | active | superseded
updated: <YYYY-MM-DD>
confidence: high | medium | low
source_repositories:
  - <仓库相对路径>
---
```

绝不要将完整源文件复制到持久化笔记中。应保留源代码链接和摘要。如果工作区已有既定的文档 schema，应遵循它，而不是引入相互竞争的新 schema。

## 阶段：`ingest`

当用户提供的笔记、决策或领域知识需要被存储，以便后续代码问题使用时使用。

1. 保留用户的原意；将用户提供的事实与代理的解释分开。
2. 在可获得时记录来源、日期、范围和置信度。
3. 检查是否已有规范笔记，进行合并而不是重复创建。
4. 标记矛盾和未知信息，不要悄悄替其解决。
5. 写入前隐去机密信息和私有标识符。
6. 在任何大范围或不可逆重写之前，展示拟写入目标和摘要。

## 阶段：`project`

用于创建紧凑的仓库 profile，帮助代理快速了解仓库。项目 profile 不能替代架构或行为文档。

### 最小 profile

```markdown
---
id: <group>/<repository>
repository_path: <相对路径>
status: active | archived | unknown
updated: <YYYY-MM-DD>
tags: [<标签>, <标签>]
related_knowledge: []
---

# <repository> profile

## 一句话用途
<仓库提供什么>

## 职责与边界
- 负责：<...>
- 不负责：<...>

## 关键能力
- <能力>

## 依赖
- 上游：<...>
- 下游：<...>
- 兄弟/集成组件：<...>

## 入口点和重要路径
- `<路径:符号>` — <作用>

## 常用验证命令
- `<安全命令>`

## 变更影响
<这里发生变更可能影响什么>

## 未知信息与所需验证
- <...>
```

### Profile 查询行为

- 在进行后缀或模糊匹配前，先解析精确的 `<group>/<repository>` 匹配。
- 如果后缀或模糊查询有多个匹配项，应列出候选项并请用户选择。
- 当存在这些字段时，`list` 应支持按组、标签、所有者/团队标签或文本进行过滤。
- `delete` 默认应执行 dry run，并要求明确确认。
- 保持 profile 简洁，链接到规范知识，而不是复制其内容。

## 写入与变更门槛

在执行任何 `archive`、`ingest` 或 `project` 写入前：

1. 说明目标文件和计划中的变更。
2. 保留无关内容，避免大范围重写。
3. 当请求存在歧义、具有破坏性或会影响外部系统时，请求确认。
4. 写入后重新读取已变更的文件，并验证链接/元数据。
5. 报告最终 diff 或文件列表。

用户提出“分析”“追踪”“理解”或“审查”请求，并不代表授权编辑源代码。

## 公共复用清理

为其他工作区创建或导出此技能时：

- 将个人姓名、账号、电子邮件、团队名称、产品名称、客户名称和内部项目代号替换为通用占位符。
- 将绝对主目录、公司仓库根目录、内部服务路径、集群名称、主机名和专有分类体系替换为 `REPO_ROOT`、`KNOWLEDGE_ROOT` 和 `<repository>` 等变量。
- 删除凭据、令牌、包含私有基础设施信息的 URL、事件标识符和组织特定的升级规则。
- 删除特殊情况排除项，除非它们表达的是通用安全原则；将其改写为可配置策略。
- 优先使用仓库相对路径示例和中性术语。

## 触发示例

- “这个配置标志控制什么？” → `ask`
- “追踪从 HTTP 处理器到持久化的请求流程，并告诉我超时变更会影响什么。” → `explore`
- “把我们刚找到的调用链记录下来。” → `archive`
- “保留这些笔记作为仓库知识，同时保留不确定性。” → `ingest`
- “为这个仓库创建一个快速 profile，并列出它的依赖。” → `project`

## Self-evolution

本 Skill 具备经验积累、评估与持续进化能力。目录（均相对本 Skill 根目录）：

```text
agents/skills/dotf-code-explore/
├── SKILL.md
├── examples/      # 经过验证的优秀执行案例
├── evals/         # 可验证成功标准
└── experience/    # 真实失败 / 成功 / 规律
```

不要为了自进化而破坏上文已规定的目标、流程、工具用法、输出与约束。

### Examples

执行复杂任务前：

1. 检查 `examples/`
2. 找到与当前任务相关的成功案例
3. 优先复用已经验证的方法

没有相关案例时按上文正常执行，不要编造案例。

### Evaluation

任务完成前：

1. 检查相关 `evals/`
2. 验证关键输出
3. 检查是否违反 Skill 约束
4. 尽可能运行相关 Eval Cases（见 `evals/cases.yaml`）

优先确定性 Eval；无法确定性判断时再用 LLM Judge。Eval 失败则先修输出，不要带着失败交卷。

### Experience

任务完成后，出现以下情况才写入 `experience/`：

- 失败
- 用户纠正
- 明显成功
- 新的有效执行方法
- 可复用的经验

不要记录 trivial information。不要伪造条目。密钥、内部 URL、凭据不得写入。

单次失败 → `experience/failures/`。重复出现的规律 → `experience/patterns/`（至少两次同类证据）。

### Evolution

只有当 Experience 暴露出**可复用、稳定的问题或模式**时，才考虑修改本 Skill。

遵循：

```text
Experience
    ↓
Repeated Pattern
    ↓
Improvement Proposal
    ↓
Eval
    ↓
Pass
    ↓
Update Skill
```

禁止：

```text
Single Failure
    ↓
Directly modify SKILL.md
```

进入 Skill 正文的 Experience 必须同时满足：可复用于多个类似任务、有足够证据、能明确改善结果、不破坏已有能力、可通过 Eval 验证。一次性特殊情况只留 Experience，不改 Skill。

实际更新生产 `SKILL.md` 时：

1. 不要直接覆盖原文；记录 version / change / reason / evidence / evaluation。有 Git 则优先靠 Git diff 留历史。
2. 若改动来自**真实执行经验**：优先委托 `skill-evolver`（`evolutions/` → 验证 → 晋升），不要本 Skill 自己改生产稿。
3. 若只是结构/规则的显式修订且环境有 `skill-upgrader`：走其 `update` 模式（`agents/skills/dotf-code-explore/patches/`），仍须先提案再应用。
4. 未展示 Proposal 并获得用户确认前，不改生产 Skill。
