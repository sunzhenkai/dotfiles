# 概念、实体、业务处理线

这三层是给人建立心智模型的核心，必须**自动识别、持续维护**，不能只在首次 build 写一次。源码与现有镜像冲突时，以当前源码为准，并在页内注明旧说法被取代。

人工锁定的段落用 `<!-- manual -->` … `<!-- /manual -->` 包住，update/build 不得改其中文字。

## 概念（concepts）

领域里需要解释的词：计费口径、状态机名、角色、协议术语、内部黑话。

**识别信号**（并存即可，不要求全中）：

- README / docs 里被定义或反复出现的术语
- 类型名、包名、配置键、枚举值
- 注释与错误文案中的稳定说法

**一页一个概念。** INDEX 是词表：

```markdown
| 概念 | 一句话 | 页 |
|------|--------|-----|
| Listing | 一次可被预订的房源快照 | [listing.md](listing.md) |
```

正文最少包含：定义、为什么存在、容易混淆的近义、出现在哪些实体/处理线/模块。没有依据时写「推断」并给路径。

## 实体（entities）

有身份、可被引用的对象：持久化记录、消息、聚合根、对外 DTO（仅当它就是领域语言时）。

**识别信号**：schema / migration / protobuf / struct / 模型类；仓储或序列化边界上的名词。

INDEX 用表格：实体 / 身份 / 生命周期 / 页。正文建议小节：

1. 是什么（一句）
2. 关键字段（名、含义、约束）— 详尽模式补全；简约只列标识与状态
3. 与其他实体的关系
4. 谁读写（模块、处理线）
5. 不变式与常见错误状态

不要把每个内部 DTO 都做成实体。胶水结构留在模块文件表即可。不要为纯结构体源文件再各建一页；详尽加深本实体页。

## 业务处理线（flows）

一次对用户或系统有意义的完整路径，不是函数调用图。

**识别信号**：HTTP/RPC 处理器、CLI 子命令、消费者/定时任务、README 中的「如何完成 X」。

INDEX：处理线 / 触发 / 输出 / 页。每一条必须能回答：

| 节 | 写什么 |
|----|--------|
| 背景 | 谁在什么场合发起 |
| 目标 | 成功时世界变成什么样 |
| 流程 | 有序步骤；简约到模块或核心符号名；详尽每步写模块 + 符号 + 失败形态 |
| 依赖 | 上游数据、服务、前置状态 |
| 输出 | 返回值、持久化、消息、副作用 |
| 失败 | 关键失败如何结束，是否可重试 |

步骤用有序列表，复杂分叉用小表格。链到实体和概念，不在流程里重新下定义。

## 维护

| 动作 | 做法 |
|------|------|
| 新增 | 源码里稳定出现且能讲清的，补页并挂 INDEX、overview 地图 |
| 更新 | `diff` 波及的符号/字段/步骤：先按 [routing.md](routing.md) 落到模块，再只改对应知识页；不要为每个变更源文件建详页。名称变更则改文件名或在旧页写跳转 |
| 删除 | 源码已消失：INDEX 移除，页顶标明废弃并链到替代；不要默默删掉 manual 块 |
| 合并 | 两个名字同一事物：留领域常用名，另一页改成别名并指向 |

build 与 update 结束前自检：每个模块 README 至少链到一个概念或处理线；每条处理线至少链到一个模块；每条切片至少链到一条处理线或一个模块；`context/` `surface/` `data/` `runtime/` `build/` 六份恢复页存在且做完 [projections.md](projections.md) 的恢复完备自检；孤页要么补链接要么删。切片与处理线分工见 [facets.md](facets.md)。
