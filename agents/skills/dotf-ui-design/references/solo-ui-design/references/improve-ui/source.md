# 改进 UI

根据实际约束该界面的系统，审计一个连贯的产品界面。保留产品身份，复用现有所有者；与其给出缺乏依据的发现，不如不报告发现。仅为用户选定的改动编写计划；由另一位智能体执行计划。

## 边界

- 绝不修改产品源代码。仅可在 `design-plans/` 下创建或编辑文件。
- 不安装依赖、不运行格式化工具、不提交、不推送，也不以其他方式修改工作区。
- 不更新设计文档。在计划中记录已接受的文档变更，供执行者处理。
- 仅当用户提供渲染证据或明确要求视觉检查时，才使用渲染证据。
- 确保每个计划都是自包含的；其执行者不具有审计或对话上下文。

## 1. 选择界面

遵守用户的范围。若请求过于宽泛，选择一个可部署应用，以及一组代表主要产品任务的连贯界面。说明该选择；不要将整个仓库整合为一个产品。

从该界面的路由和布局开始。沿渲染路径追踪组合、共享组件、变体、解析后的令牌和样式。不要从全仓库范围的不一致性搜索开始。

只有通过渲染、导入、props、解析后的配置、CSS 继承或该界面加载的生成产物证明时，连接才存在。共用名称、相似令牌、仓库邻近性和概念关系都不能建立连接。除非参与已追踪的路径，否则排除其他应用、预览、配置器、生成的注册表、遗留系统和企业变体。

## 2. 重建局部系统

检查 `DESIGN.md`、仓库指南和界面局部的设计文档。仅在证明某个来源仍然有效且约束所选界面后使用它；除非被明确接受且仍然有效，草稿、提案、迁移和任务清单仅描述未来意图。缺少设计文档并非一项发现。

只检查与已追踪路径相关的令牌、变量、主题、原语、变体和组合。将别名和变体解析至其定义。仅当仓库明确说明时，才将实现归类为局部或遗留实现。

记录：

```markdown
## 设计语言
- 已审计界面：
- 设计来源：
- 已记录决策：
- 约束所有者与使用方：
- 明确例外：
```

除非被引用的来源明确标识了例外，否则在 `明确例外` 下填写 `未记录`。

## 3. 证明发现

在应用证明门槛之前，检查每个已追踪界面的面向用户标签、激活状态呈现、响应式分支和同级变体，寻找内部矛盾。仅将结果视为候选项。

仅当修正主要改变视觉呈现、界面文案、布局、组件样式或对已记录设计规则的遵从性时，该发现才在范围内。如果修正主要改变产品行为是否正常工作，则拒绝它。

搜索结果、重复和实现差异产生的是候选项，而非发现。仅当以下三项证明均存在时才保留候选项：

1. **契约** — 为该属性和范围引用一项有约束力的设计决策，或引用同一任务内面向用户呈现或内容的直接矛盾。“优先”“通常”、名称、省略、重复以及没有例外，均不能建立契约。
2. **运行时** — 证明所引用的所有者、值或行为通过已追踪的运行时路径到达受影响界面。不要比较不同的所有权层或生命周期状态。
3. **修正** — 陈述一项由证据要求的改动。如果它依赖现有令牌、变体、原语或范例，请准确命名。如果证据无法确定正确选择、预期状态含糊、提案包含替代方案，或修正需要虚构产品意图，则拒绝该候选项。

源代码可以证明令牌、排版、颜色、间距、布局、文案、组件变体、响应式呈现和显式设计契约违规。它不能将功能行为、状态管理或交互正确性转化为设计发现。层级、显著性、密度、清晰度、可发现性、可用性和感知一致性需要渲染证据或用户证据。

除非用户明确要求，否则舍弃无障碍和 HTML/ARIA 语义发现。除非用户要求，或有产品特定的设计契约约束它们，否则舍弃路由损坏、重定向、数据接线、操作失败、元数据、包 API、性能、架构和代码质量发现。

仅在所有证明通过后分配置信度。证据支持时复用现有所有者；不要仅根据重复创建共享原语。

## 4. 审核发现

报告前，重新打开每个引用的来源，并尝试证伪每个候选项。出现以下情况时删除它：

- 问题与所引用的实现并不完全匹配。
- 规则并不约束该属性和界面。
- 反证表明差异有效或是有意为之。
- 证据支持多种修正方案。
- 修正虚构了产品意图。
- 另一项发现描述了相同的根本问题。

只有通过此轮审核的发现才能进入表格。

## 5. 报告

按置信度、用户影响、覆盖范围和修正成本对通过的发现排序。最多保留三项。

使用此结构：

```markdown
## 设计语言
- 已审计界面：
- 设计来源：
- 已记录决策：
- 约束所有者与使用方：
- 明确例外：

## 发现
| # | 问题 | 证据 | 建议改动 | 范围 | 置信度 |
| --- | --- | --- | --- | --- | --- |

## 优先改进
<最有杠杆效应的发现及原因；若没有，则写无支持的建议。>
```

证据必须建立契约、运行时关系和确定性的界面后果。拟议改动必须包含一项修正。返回前删除缺乏支持或重叠的行。

删除未包含所有必填列（包括置信度）的任何发现。

在 `优先改进` 下，选择证据最强且最具杠杆效应的一项通过发现。绝不合并发现。

如果没有候选项通过，请在 `## 发现` 下写入 `未发现有充分支持的问题。`，并在 `## 优先改进` 下写入 `没有有充分支持的建议。`。

如果有发现通过，停止并询问要将哪些转化为计划。如果用户已经选择了一项发现，或明确要求为某个已描述的改进编写计划，请在该范围内继续。如果被要求直接修复或改进，请提供计划；绝不实施它。

## 6. 明确选定改动

阅读 [references/plan-template.md](references/plan-template.md)。每项选定改动编写一份计划，绝不按症状分别编写。

编写前，重新打开每个引用的来源；在可用时记录当前提交；识别可精确复用的原语和范例；并追踪受影响的界面。协调现有计划，而非复制一份。

当仓库提供令牌或组件契约时，不要虚构值。仅在证明现有系统为何无法表达该决策，以及哪些使用方应共享它之后，才引入原语。

如果被要求协调，请根据当前源代码和已记录的决策重新检查现有计划；更新过期的证据、受影响界面和状态。
