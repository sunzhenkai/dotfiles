# 质量画像

术语见 [../CONTEXT.md](../CONTEXT.md)。只在复杂档强制：它是完成判据的约束，不是独立文档，也不要求穷举质量标准的全部维度。不做自动评分器——字段是否齐全、底线能否验证，由审阅者按 P 级判定。

## 字段

```text
受众与场景: <谁在什么场景完成什么>
规模与运行假设: <人数、并发、数据量、本地 / 共享 / 生产>
页面/主流程: <3-7 条，每条一个入口到一个结束状态>
角色底线:
  product: <核心工作流、范围外、协作边界>
  design: <视觉方向、关键页面、必备状态、可用性与无障碍底线>
  engineer: <数据一致性、并发、错误边界、测试与本地启动证据>
显式降级:
  - 维度: <如持久化方式、实时协作、移动端适配>
    默认期望: <画像其余字段自然推出的要求>
    实际选择: <本次接受的实现>
    原因: <范围或约束>
    确认状态: <confirmed | pending>
```

- 五个顶层字段都要写；`角色底线` 下的 product、design、engineer 三条一条都不能省。
- 主流程 3-7 条。超出 7 条说明范围过大，按「不做的事」收敛，不堆清单。
- 每条底线写成可检查的话：点出页面或状态、并发与数据量假设、以及验证方式（运行、截图、测试、启动步骤）。「高质量」「体验好」「足够健壮」这类形容词不算。
- 某维度确实不适用：写「不适用」加一句原因，不留空，不默默省掉字段。

## UI 交付的 design 底线必须回答

画像覆盖含界面交付时，`角色底线.design` 除视觉方向、关键页面、必备状态外，还必须能用一句话回答四个契约问题；回答不出按「空泛形容词」归 P0，复用缺字段判定。确实不适用写「不适用」加一句原因。

```text
控件密度: <哪些 surface 用常规档、哪些用密集档；同一上下文内是否要求同高>
icon 形态: <是否单一 icon primitive（固定方盒 + SVG + 尺寸 token）；是否禁止裸字符/emoji 充当 icon>
表单间距: <字段间距与表单收尾间距是否来自 token，而非手写数值>
证据分工: <哪些一致性要求用 DOM/静态断言钉住，哪些必须截图确认>
```

- 四问只约束「底线要写清」，不规定具体取值；取值由设计决定，写清即可。
- 「证据分工」必须写验证方式，与「每条底线带验证方式」同一条纪律。

## 与交付标准的分工

复杂档下画像收编交付标准里的三类：验证或测试覆盖、错误与边界行为、运行假设。这三类不再重复写进「交付标准」；「交付标准」只写画像未覆盖的交付面，例如文档与配置等配套更新。简单和中等不写画像，交付标准照旧。

## 显式降级

- 判定看实质，不看措辞：凡比默认期望少交付的都是降级，改名成「技术选型」「本期简化」也一样算。
- 方案完善阶段一次列出所有已知生产性降级，初始状态一律 `pending`。
- 只有用户能改 `confirmed`：点名接受该项，或明确说按降级表全部确认。执行者、审阅者、评审收敛都不算确认。
- 实现中发现新的降级：补进降级表，回到同一确认门，不静默接受。
- 仍有 `pending` 时按退出点「降级未确认」停：不开工、不交接。

## 缺字段怎么判

派审时把完成判据原文、画像原文、显式降级原文一并贴上。缺任一必要字段、字段写成空泛形容词、或核心底线没有验证方式：记 P0，路由写成 `完善中：补质量画像并再审。此阶段不改代码。`，不开工。确实写不出——说不清受众与场景，或主流程完全未知且会改方案——才走退出点「理解不够」。

画像不引入新的审阅对象：架构、接口、schema、代码骨架仍在「不审」列里。写不出某条底线不等于要先做大设计，按上一段判 P0 或走「理解不够」。

## 交接与完成门

- 复杂档交接给 task-explore 时逐字带上画像原文快照，含显式降级表；路径或小节指针只作辅助，不能替代快照。后续设计、子任务的验收标准引用同一份原文。
- 完成门：字段齐全，`pending` 降级数为 0；`confirmed` 降级在验证记录里可追踪。
