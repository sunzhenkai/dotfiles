# Task Wizard：任务完成方案

产出**步骤级**任务完成方案。不做详细设计——不画架构、不定接口、不写代码骨架。

## 先分流

- **Goal 方案**：这次调用处在 goal 里。消息里看得到 `/goal`，或当前有进行中的 goal 且本条消息挂了本 skill。读完「原则」后只执行「Goal 方案」。写完方案后：复杂档先做完「外部参照」再审阅；简单和中等直接审阅。然后进入循环：评审（定级 + 改进意见）→ 修改方案 → 再评审。改进意见为「已达到预期」才进入「写完之后」。
- **任务方案**：没有进行中的 goal。只执行从「工作流」到「边界」各节。写完停下，等人选择。

## 原则

- **先查后问**：能查到的（代码、文档、环境）先查，只有自己拿不准时才问；问前必给推荐答案。
- **步骤级颗粒度**：每步一个可执行动作，不超过 2 行，含「要点」与「验证方式」。
- **阻塞点与坑必须显式列出**，没有就写「无」，不许省略小节。
- **简洁**：方案总篇幅控制在半屏内，是行动清单不是文档。

## 工作流（任务方案）

1. **澄清意图**：一句话复述目标与完成标准。歧义会影响方案走向时才提问（带推荐答案）；否则按最合理解释推进，并在「假设」中声明。
2. **摸底现状**：只读探查相关代码 / 文档 / 环境，把「已确认事实」与「假设」分开。
3. **外部参照**：摸底后的档位是复杂，或写到定稿前升到复杂时，读并做完 [references/external-precedent.md](references/external-precedent.md)。简单和中等跳过。做完再写建议路由。
4. **产出方案**：按下方模板输出，并给出「复杂度路由」建议。
5. **对齐**：末尾问用户「按此执行 / 调整哪步 / 改路由」，不要默认直接开干。

## 输出模板（任务方案）

```markdown
# 任务方案：<任务名>

## 目标
<一句话说清完成标准>

## 前提
- 事实：<已查证的现状>
- 假设：<未查证，方案基于此>

## 步骤
1. <动作> — 要点：…；验证：…
2. <动作> — 要点：…；验证：…

## 阻塞点
- <会卡住整个方案的事，以及需要先解决什么；无则写「无」>

## 坑 / 注意事项
- <易踩的坑、隐性依赖、顺序敏感点；无则写「无」>

## 不做的事
- <明确排除项，防止范围蔓延>

## 建议路由
<简单 / 中等 / 复杂 之一 + 一句话理由>
```

## 复杂度路由（任务方案确认后的衔接）

按复杂度三选一，写进方案「建议路由」小节；用户可改。拿不准时往简单靠一档并说明理由。

| 复杂度 | 信号 | 衔接 |
|--------|------|------|
| 简单 | 步骤少、单仓单模块、无契约/schema 变化、可逆 | 本方案即 plan，先走 grill-with-docs 拷问方案、梳理清楚，再按步骤直接实现，不再产其他工件 |
| 中等 | 在简单之上，需 spec 契约或正式验收 | 先走 grill-with-docs 拷问梳理，再走 OpenSpec：委托 `openspec-propose`，经 `openspec-apply-change` 实施 |
| 复杂 | 多阶段/多子任务、跨仓跨模块、需编排或并行 | 走 task-explore → taskflow：先 task-explore，把本方案正文登记进 `TASK.md` 的「方案」小节（步骤 / 阻塞点 / 坑），再经 `explore`/`design`/`decide` 梳理清楚后 `handoff`，由 taskflow 建 `{task}-driver` 并委托 stock `openspec-*` 实施 |

- 路由是**衔接不是执行**：task-wizard 只把方案与结论交给对应流程，不代替它们做提案或编排。
- **先拷问后实现**：只约束任务方案。简单 / 中等两档实现前一律走 grill-with-docs，把方案里没想清的分支拷问掉再动手，不跳步。
- 委托 `grill-with-docs` / `openspec-*` / task-explore / taskflow 前确认当前环境能读到对应 skill；不可用时停下报告并给出安装选项（如 `dotf agents -c`），不自行发明等价命令。
- 路由到 grill-with-docs 时，逐字保留其两跳调用（`grilling` + `domain-modeling`），不简写、不替换。
- 路由到 task-explore 时，**逐字带上方案正文**（目标 / 事实 / 假设 / 步骤 / 阻塞点 / 坑 / 不做的事），并点名落点：`new` 时登记进 `TASK.md` 的「方案」小节；只作输入，不下新任务名、不重演探索。
- 复杂档的正文在交出前已含外部参照：对上出处的在事实里，对不上的在假设里。上述原文原样带给 task-explore。
- 路由到 OpenSpec / taskflow 时，把方案正文（目标、步骤、阻塞点、坑）作为任务描述原文带入，不让下游重新猜意图。

## 边界（任务方案）

- 任务方案里涉及线上环境（生产、预发、共享远程）的步骤，标注「需逐步授权」，不在方案阶段执行。
- 发现任务实际是「写详细设计 / 直接改代码 / 排查 bug」时，说明并退出本流程，不硬套模板。

## Goal 方案

写给正在执行 goal 的 agent。正文自洽：之后的回合只重读已经写下的方案。方案只出现在当轮回复前部，不落文件。完成判据是一条可检查的话，写在方案里，用它判断做完没有。用户已经发出的 goal 原文保持原样。

术语见同目录 `CONTEXT.md`。

状态只允许 `执行中`、`已停`、`已交接`、`已完成`。退出、升档、交接、做完时改写状态与路由，使最后一份方案等于当前状态。

### 不套模板

原因还不清、要先排查的，以及要定接口或架构的详细设计：不套下面的步骤正文，不新增工作。回复仍写出状态 `已停` 与路由。

- 排查：`已停。你明确说走 task-explore 之后再继续。`
- 详细设计：`已停。本流程不做详细设计。`

### 正文

没有的小节写「无」。半屏放不下时压缩前提和坑；完成判据、步骤、退出点、方案置信度、状态、路由保留。假设一旦被打穿就会改步骤或完成判据的，不开工，状态写 `已停`，走退出点「理解不够」。

```markdown
# Goal 方案：<任务名>

## 完成判据
<一条可检查的话>

## 前提
- 事实：…
- 假设：…

## 步骤
1. <动作> — 要点：…；验证：…

## 阻塞点
- 无

## 退出点
- 理解不够；阻塞解不开；未点名的危险操作；线上动作；同一验证连败两次；泄密；执行中升档；审阅不通过；审阅派不出；审阅没有结论
- 命中任一标签后把状态改为已停，路由写成需要的授权。单独「继续」不算授权。危险操作在任务点名后可以做；线上动作与泄密即使任务点名也停。
- 本任务另有：无

## 坑
- 无

## 不做的事
- …

## 方案置信度
<高 / 中 / 低>

## 状态
执行中

## 纪律
- 执行中：路由以「完善中」开头时，只改正方案并再审，不执行步骤里的实现。否则从第一个未验证步骤做。判据成立就改为已完成。
- 已停：只做已经点名的那一件授权。单独「继续」仍停。
- 已交接：不重出方案。按路由里的账本继续。账本做完且完成判据成立才改为已完成。
- 改步骤：完善中可以改完成判据和步骤。离开完善之后，仅当状态仍是执行中、完成判据不变、档位仍是简单。
- 审阅：每轮同时给出定级和改进意见。改进意见为「已达到预期」才进入「写完之后」。否则把改进意见写入完成判据与步骤，再评审。不因此已停，不改代码。只有审阅者非常确信对照已有知识、已有方案、公开方案也无法再完善以达到预期时，才停，退出点「审阅不通过」，并写明该结论。

## 路由
<当前状态的下一跳>
```

### 外部参照

本仓摸底后的档位是复杂，或写到定稿前升到复杂：读并做完 [references/external-precedent.md](references/external-precedent.md)，把结果写入前提，然后才审阅。简单和中等跳过，直接审阅。建议路由在这次之后按事实重判，可以低于初步档位。

### 审阅

写完方案、改代码之前做一次。状态为 `执行中` 且出现新的决策点时再做一次。状态为 `已交接` 时，已交给下游的步骤不重写；出现新的决策点时再审，低或中则完善尚未开始的步骤并再审，不因档位改回 `已停`。

执行者写不出方案时，退出点用「理解不够」，到此为止。

方案里已经有线上动作、泄密、或未点名的危险操作：状态改为 `已停`，到此为止。

审阅者只读，不改工作区。一次审阅返回定级和改进意见。改进意见写清改哪一条完成判据或步骤，并指回已有知识、已有方案或公开方案。已达到预期时，改进意见写「已达到预期」。非常确信无法再完善以达到预期时，另给诚实结论。术语见 `CONTEXT.md`。

人选：

- goal 原文或当轮用户消息写了 `agent-roster`：委托 `$agent-roster` 做名册审阅。点名了唯一 Endpoint 就走它的快速路径。只说用名册、没点名谁：按它的 routing 选一个最匹配的直接派，不列候选表。执行器不可用、证据不足、或还要人：状态改为 `已停`，退出点「审阅派不出」。
- 其余情况：当前宿主拉起的子 agent。宿主能分出更强模型时用更强的一档；给不出排序时用该宿主的最强档。当前模型已是最强档时，仍另起一个同模型子 agent，并在前提的事实里记「无更强档」。起不来就换下一个可用模型，最多两次。两次都没有审阅结论：状态改为 `已停`，退出点「审阅没有结论」。

审阅者是另一个子 agent，或名册上的 Endpoint。执行者自己给出的定级不算审阅结论。

循环是：出方案 → 评审（定级 + 改进意见）→ 修改方案 → 再评审。定级不是循环的出口。

只有定级、没有改进意见、也没有诚实结论：再叫一次审阅者补改进意见。第二次仍没有：退出点「审阅没有结论」。

- **改进意见为「已达到预期」**：把此前改进意见写入步骤。再核对退出点，撞上就 `已停`。然后进入「写完之后」。
- **诚实结论**：审阅者非常确信，对照已有知识、已有方案、公开方案，也无法再进一步完善以达到预期。`已停`，退出点「审阅不通过」。回复写明预期，以及这三处为什么补不上。定级为低或中、同一缺口还在，本身不是这个结论。给出结论前须已对照过这三处；还有一处能指出改法时，写成改进意见并继续循环。简单和中等不把每一轮都做成外部参照；缺口可能被公开做法补上、且还没对照过公开方案时，先对照再下结论。
- **其余**：进入完善。把本轮每条改进意见写入完成判据或步骤。低且改进意见里有可检查的完成判据时，用它替换判据。两条改进意见冲突时，采纳能让完成判据可检查的那条，另一条写入坑。路由写成 `完善中。按本轮改进意见改正方案，再评审。此阶段不改代码。` 状态保持 `执行中`。接着再评审。不向用户索取「仍按此方案执行」或「按审阅建议改方案」。

用户在完善期间明确说「仍按此方案执行」：停完善，按当前已写下的步骤进入「写完之后」。不主动索取这句。

进入「写完之后」：简单档改为 `执行中` 并接着做。中等档改为 `已交接`，按「写完之后」的中等路由开工。复杂档保持 `已停`，仍等用户说走 task-explore。

### 旧方案

读到没有「状态」的 Goal 方案：路由为 `本会话直接做` 时按 `执行中` 续做，并在当轮回复补上状态。路由以 `先停` 开头时按 `已停` 处理，并在当轮回复补上状态。

读到没有「方案置信度」的 Goal 方案：先走「审阅」，再按档位续做。

读到因审阅档位为中或低而 `已停` 的方案：不要再等授权。把当时未写入的建议写入完成判据与步骤，路由改为完善中，再审。

### 写完之后

只在改进意见为「已达到预期」、该轮改进意见已写入步骤、退出点已再次核对之后，才进下面三档。拿不准档位时往简单靠一档，除非信号已经表明要改契约或要拆多段。

- **简单**（步骤少、单仓单模块、无契约或 schema 变化、可逆）：状态 `执行中`。路由写 `从第一个未验证步骤做到完成判据或退出点。` 同一轮接着做，允许随后改代码。
- **中等**（在简单之上，需 spec 契约或正式验收）：状态改为 `已交接`。同一轮开始衔接。路由固定为：`已交接。审阅者已经拷问过方案。直接 openspec-propose，再 openspec-apply-change。方案正文原样带入。进度只认该 change 的 tasks.md checkbox。全勾且完成判据成立才改为已完成。未完则下轮从第一个未勾项继续，不重出方案。`
- **复杂**（多阶段、多子任务、跨仓跨模块、需编排或并行）：建议已在步骤里。同一轮只出方案，不动代码。状态 `已停`。路由固定为：`已停。你明确说走 task-explore 之后：没有 tasks/ 先等确认再创建；slug 由 task-explore 推断，不另起任务名；new 时把完成判据、步骤、阻塞点、坑登记进 TASK.md「方案」；然后由你选 explore 或 chat；decide 用完成判据当成功标准；你确认冻结后才 handoff。--goal 带上目标、完成判据和采纳方案。然后把状态改为已交接。创建目录、冻结、脏工作区选择是下游门禁，不标完成，不重出方案。进度只认 driver 的 tasks.md checkbox。全勾且完成判据成立才改为已完成。`

中等档在改进意见为「已达到预期」时已经是 `已交接`，下一跳是 `openspec-propose`。复杂档要等用户说走 task-explore，然后把状态改为 `已交接`。handoff 之前路由是 task-explore 的当前阶段，handoff 之后是 driver 的第一个未勾项。

下游 skill 读不到时停，状态保持 `已停`，给出安装选项，不自行发明等价命令。

中等在 `已交接` 后发现要拆多段：停止改代码，状态改回 `已停`，路由换成复杂档那句，等用户再说走 task-explore，不自动建 driver。

checkbox 全勾但完成判据不成立：状态改为 `已停`，不标完成。汇合时以本方案里的完成判据为准。

### 退出点

判定：

- **理解不够**：写不出一条可检查的完成判据，或步骤主体靠会改方案的猜测。执行者写方案时就能判定的，直接 `已停`。进入评审循环之后，写不出判据改由改进意见或诚实结论处理，不用这个标签代替循环。
- **审阅不通过**：审阅者非常确信，对照已有知识、已有方案、公开方案，也无法再进一步完善以达到预期。回复写明预期，以及这三处为什么补不上。定级为低或中、同一缺口还在，本身不是这个标签。
- **审阅派不出**：该走名册审阅时，执行器不可用、证据不足，或还要人。
- **审阅没有结论**：本机子 agent 换过一次后仍没有审阅结论。或者连续两次审阅只有定级、没有改进意见、也没有诚实结论。
- **阻塞解不开**：有当轮解除不了的阻塞点。
- **未点名的危险操作**：任务描述没点名这些动作就停：破坏性 git、删除或不可逆改写、改密钥或权限、对外发送、不可逆迁移。点名了就做。
- **线上动作**：一律停，任务描述里写过也停。范围：直接改线上数据，以及生产、预发、共享远程上的合入、打 tag、推默认分支、部署。每一步单独要授权。
- **同一验证连败两次**：同一条验证连续失败两次，且没有新事实。
- **泄密**：密钥、令牌、内部 URL 或公司代码要写进公开仓库。始终停。
- **执行中升档**：开工后发现已是中等或复杂。立刻停，不再改代码。已经改过的可逆部分留在工作区，退出说明里写清，不自动回滚。状态改为 `已停`，路由换成「写完之后」里中等或复杂的交接句。

同时撞上多条时一次说清。命中后状态改为 `已停`，路由写成需要的授权，不把 goal 标成完成。`已交接` 期间命中同样改回 `已停`。

### 授权

授权是用户明确接受某条已经点名的动作或路由的那条消息。单独的「继续」只重申仍停着，状态保持 `已停`，不新增工作。

撞上退出点后不新增工作，不把 goal 标成完成。回复写明退出点和需要的授权。下一轮仍没有授权，就只重申这个状态。

### 执行中改步骤

离开完善之后：完成判据不变、状态仍是 `执行中`、档位仍是简单、没撞上其他退出点时，在后续回复里改正步骤，按新步骤继续。完成判据要改、升档、或撞上其他退出点：停。完善期间的改正不受本段限制。

### 做完
