# Goal 方案新增可检查的「交付标准」，防止 demo 化与过度设计

- target: agents/skills/task-wizard
- mode: update
- patch: 20260925-065234-delivery-standard
- risk: medium
- status: proposed

## Intent

用户反馈：按 goal 流程走完后实现效果简陋、像 demo。根因是方案约束只要求「一条可检查的完成判据」＋「每步 ≤2 行」，且审阅边界明确不审「判据之外的新行为」，导致交付面（验证覆盖、错误路径、文档/配置等配套更新）被系统性漏掉，同时没有任何反过度设计的约束。

要改变的行为：Goal 方案与任务方案在完成判据之外，增加可检查的「交付标准」小节，只取与本任务相关的交付面（验证或测试覆盖、错误与边界行为、文档与配置等配套更新），并有明确的克制条款（不引入超出任务所需的架构、抽象或配置项）。审阅环节把「漏交付标准」定为 P1、把「列了超出任务所需的项」纳入步骤确定环节的审；简单/中等/复杂档的「做完」都要求交付标准全过。

非目标：不改变状态机、复杂度路由、派审人选、退出点与授权机制；不引入详细设计要求。

## Conflict check

与 openspec-propose / taskflow 衔接不冲突：方案正文（含交付标准）原样带入下游，下游账本机制不变。与「不做详细设计」边界不冲突：交付标准是可检查的验收要求，不含架构、接口或代码骨架。CONTEXT.md 术语同步新增，避免与其他术语歧义。

## Rationale

交付级质量来自「验收面显式化」而非更长的方案：判据管结果对不对，交付标准管交付面全不全；审阅 P1 提供强制力，「不做的事」与克制条款防止反向膨胀（把不相关维度写成过度工程）。改动可验证：审阅者可逐条判定「漏了任务应有的交付面」，做完判定可机械检查。
