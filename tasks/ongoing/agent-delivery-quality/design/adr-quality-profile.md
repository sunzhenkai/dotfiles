# ADR: 复杂 Goal 使用质量画像作为完成判据的约束

## 状态

Proposed

## 背景

复杂产品交付的完成判据常被写成布尔功能项。上一轮 task-manager 每个功能动词都有对应实现路径，但缺少 UI、交互状态、数据并发和角色底线，结果交付成 demo。ISO/IEC 25010 把软件质量拆成功能适合性、性能效率、兼容性、交互能力等维度，并明确质量要满足干系人的显式与隐含需求（出处：https://iso25000.com/en/iso-25000-standards/iso-25010 ）。这说明「功能存在」不是质量的充分条件。

## 决策

复杂 Goal 方案 MUST 附带一小节「质量画像」。它是完成判据的约束，不是独立文档，也不要求每个项目穷举 ISO 全部维度。最小字段固定为：

```text
受众与场景:
规模与运行假设:
页面/主流程:
角色底线:
  product:
  design:
  engineer:
显式降级:
```

- `product` 写核心工作流、可见范围与协作边界。
- `design` 写方向、关键页面、必备状态、可用性/无障碍底线。
- `engineer` 写数据一致性、并发、错误边界、测试与本地启动证据。
- `显式降级` 每条写「维度 / 默认期望 / 实际选择 / 原因 / 确认状态」。缺确认的降级视为 P1。
- 只在复杂档强制。复杂档判定沿用 task-wizard，且命中任一产品交付硬指标即复杂：多个主页面、两个以上生效角色/权限边界、跨请求或用户复用的持久化数据、外部集成/实时协作/通知/审计等跨模块行为、项目级重构或业务逻辑复杂且涉及面广。
- 复杂档下，画像收编现有「交付标准」中的验证/测试、错误边界与运行假设；「交付标准」只写画像未覆盖项。
- 降级确认不属于审阅授权：`pending` 必须由用户确认后才可改 `confirmed`；有 pending 时阻塞 decide/handoff。

## 影响

- task-wizard 的复杂 Goal 初审把缺画像或降级未确认视为 P0/P1，阻止开工。
- 复杂档初审改走 `role-based-reviewer roles=product,design,engineer mode=review`；其余档位不强制。
- 画像原文进入 task-explore、design、taskflow proposal 和验收标准，避免中途丢失。
- Skill 改动保持通用：不写 task-manager 专有页面、数据库名或机器路径。

## 回退

新增规则只影响复杂档；回退时删除对应 patch 的生效行，恢复既有审阅与验收模板。已产出的项目方案可继续按新画像补审，不需要迁移历史交付物。
