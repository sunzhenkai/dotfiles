# task-wizard-goal Specification

## Purpose

定义处在 goal 里时 Goal 方案的可重入状态与路由下一跳。派审贴上完成判据与「不做的事」。意见分 P0/P1/P2。评审是否通过只看完成程度是否为高。有 P0 或 P1 时不得判高。没有未消失的 P0/P1 则收敛；P2 写入坑后不再审。同一条 P0/P1 再核仍在则「审阅不通过」。完成判据和下游账本汇合后才标完成。

## Requirements

### Requirement: Goal 方案与任务方案分流

处在 goal 里（消息中有 `/goal`，或已有进行中的 goal 且本条消息挂了 task-wizard）时，系统 MUST 只产出 Goal 方案。没有进行中的 goal 时，系统 MUST 只走任务方案，并在写出后停下等人选择。任务方案的确认、三档路由与边界 MUST 保持原有行为。

#### Scenario: 处在 goal 里不写任务方案

- **WHEN** 消息中有 `/goal`，或已有进行中的 goal 且本条消息挂了 task-wizard
- **THEN** 回复前部是 Goal 方案
- **THEN** 不出现任务方案的「按此执行 / 调整哪步 / 改路由」对齐问句

#### Scenario: 没有 goal 时不进入 Goal 方案

- **WHEN** 没有进行中的 goal，且消息中没有 `/goal`
- **THEN** 只产出任务方案并停下等人选择

### Requirement: 方案正文携带状态与下一跳

Goal 方案 MUST 写在当轮回复前部，MUST NOT 落成文件。正文 MUST 含完成判据、步骤、退出点、方案置信度、状态、路由。状态只允许 `执行中`、`已停`、`已交接`、`已完成`。方案置信度只允许 `高`、`中`、`低`。路由 MUST 只描述该状态的下一跳。退出、升档、交接、做完时，系统 MUST 改写状态与路由，使最后一份方案等于当前状态。

#### Scenario: 半屏不够时仍留下状态机

- **WHEN** Goal 方案超过半屏
- **THEN** 可以压缩前提与坑
- **THEN** 完成判据、步骤、退出点、方案置信度、状态、路由仍在

#### Scenario: 旧方案没有状态行

- **WHEN** 后续回合读到一份没有「状态」的 Goal 方案
- **THEN** 路由为 `本会话直接做` 时按 `执行中` 续做，并在当轮回复补上状态
- **THEN** 路由以 `先停` 开头时按 `已停` 处理，并在当轮回复补上状态

### Requirement: 四个状态的下一跳

路由以「完善中」开头时，`执行中` MUST 只改正方案并再审，MUST NOT 执行步骤里的实现。否则 `执行中` MUST 从第一个未验证步骤继续，直到完成判据成立或改为 `已停`。判据成立时 MUST 改为 `已完成`，停止新增工作，并对照判据说明；环境能把 goal 标成完成时 MUST 标完成。`已停` MUST 只执行用户已经点名授权的那一件事。单独「继续」MUST NOT 构成授权，状态保持 `已停`，且不新增工作。`已交接` MUST NOT 重出 Goal 方案；按路由中的账本继续。该账本的完成条件成立且完成判据成立时，才改为 `已完成`。完善期间可以改完成判据和步骤。离开完善之后，改步骤 MUST 仅在状态为 `执行中`、完成判据不变、档位仍为简单时发生。

#### Scenario: 简单档跨回合续做

- **WHEN** 状态为 `执行中`，本轮未做完，下一轮 skill 不再挂上
- **THEN** 从第一个未验证步骤继续
- **THEN** 不把方案重写成任务方案

#### Scenario: 单独继续仍停

- **WHEN** 状态为 `已停`，用户只回复「继续」
- **THEN** 状态仍为 `已停`
- **THEN** 不新增工作，不把 goal 标成完成

#### Scenario: 完成判据成立

- **WHEN** 状态为 `执行中` 且完成判据成立
- **THEN** 状态改为 `已完成`，停止新增工作，回复对照判据说明已完成
- **THEN** 环境能标完成时把 goal 标成完成

### Requirement: 不套模板仍留下已停

原因还不清要先排查，或要定接口、架构的详细设计时，系统 MUST NOT 套用完整步骤正文，MUST NOT 新增工作。回复 MUST 仍写出状态 `已停` 与路由：排查指向等用户明确说走 task-explore；详细设计标明本流程不做。

#### Scenario: 排查停在 task-explore 入口

- **WHEN** Goal 任务要先排查、写不出可执行步骤
- **THEN** 不写步骤正文，不新增工作
- **THEN** 状态为 `已停`，路由等用户明确说走 task-explore

#### Scenario: 详细设计直接停

- **WHEN** Goal 任务要定接口或架构
- **THEN** 状态为 `已停`，路由标明本流程不做详细设计
- **THEN** 不新增工作

### Requirement: 退出点改写为已停

方案 MUST 列出这些退出点标签：理解不够、阻塞解不开、未点名的危险操作、线上动作、同一验证连败两次、泄密、执行中升档、审阅不通过、审阅派不出、审阅没有结论。方案 MUST NOT 把「方案置信度不足」列为退出点。正文 MUST 写明：命中后把状态改为 `已停`，路由写成所需要的授权；单独「继续」不算授权。危险操作在任务描述点名后可以做；线上动作与泄密即使任务描述点名也 MUST 停。`已交接` 期间命中退出点 MUST 把状态改回 `已停`。退出点 MUST NOT 把 goal 标成完成。多条同时命中时 MUST 一次说清。

#### Scenario: 退出后路由不再是开工句

- **WHEN** 执行中撞上退出点
- **THEN** 状态改为 `已停`，路由点名需要的授权
- **THEN** 不把 goal 标成完成

#### Scenario: 交接期间泄密仍停

- **WHEN** 状态为 `已交接`，且下一步要把密钥、令牌、内部 URL 或公司代码写入公开仓库
- **THEN** 状态改回 `已停`
- **THEN** 不新增写入，不标完成

### Requirement: 升档改路由而不终局

开工后发现已是中等或复杂时，系统 MUST 立刻停止改代码，把状态改为 `已停`，并把路由换成对应档位的交接句。已经改过的可逆部分留在工作区，MUST NOT 自动回滚。

#### Scenario: 简单档执行中升为复杂

- **WHEN** 状态为 `执行中`，执行中发现任务已是项目级重构、逻辑重塑，或业务逻辑复杂且涉及面广
- **THEN** 停止改代码，状态改为 `已停`
- **THEN** 路由改为复杂档交接句，不再保留「本会话直接做」

### Requirement: 中等路由实施到 checkbox

评审收敛、档位为中等时，系统 MUST 把状态改为 `已交接`，MUST 直接 `openspec-propose` 再 `openspec-apply-change`，方案正文原样带入。该路径 MUST NOT 等待用户说走 OpenSpec，也 MUST NOT 走 grill-with-docs。进度 MUST 只认该 change 的 `tasks.md` checkbox。全勾且完成判据成立才改为 `已完成`。未完则下一轮从第一个未勾项继续，MUST NOT 重出 Goal 方案。下游 skill 读不到时 MUST 停并给出安装选项，MUST NOT 发明等价命令。

#### Scenario: 中等且评审收敛后直接进入 OpenSpec

- **WHEN** 评审已收敛，且档位为中等
- **THEN** 状态为 `已交接`
- **THEN** 当轮开始 `openspec-propose`，不走 grill-with-docs

#### Scenario: 提案写完仍不算做完

- **WHEN** `openspec-propose` 已完成但 `tasks.md` 仍有未勾项
- **THEN** 状态为 `已交接`
- **THEN** 不把 goal 标成完成，下一轮从第一个未勾项继续 apply

### Requirement: 复杂路由遵守探索门禁
评审收敛、档位为复杂时，本轮 P2（若有）MUST 已经写入坑。同一轮 MUST 只出方案、不改代码，状态为 `已停`，直到用户明确说走 task-explore。其后状态为 `已交接`。路由 MUST 写明：没有 `tasks/` 时先等用户确认再创建；slug 由 task-explore 推断，wizard MUST NOT 另起任务名；`new` 时把完成判据、步骤、阻塞点、坑登记进 `TASK.md` 的「方案」；`new` 之后由用户选择 explore 或 chat；`decide` 用完成判据作为成功标准；用户确认冻结后才 `handoff`。交接前的创建目录、冻结、脏工作区选择是下游门禁，MUST NOT 标 goal 完成，也 MUST NOT 重出 Goal 方案。`handoff` 之后进度只认 driver 的 checkbox。driver checkbox 全勾且完成判据成立才改为 `已完成`。中等路径在交接后发现已是项目级重构、逻辑重塑，或业务逻辑复杂且涉及面广时，MUST 把状态改回 `已停` 并换成复杂路由，等用户再说走 task-explore。

#### Scenario: 未授权不创建探索任务

- **WHEN** 评审已收敛，档位为复杂，且用户尚未说走 task-explore
- **THEN** 状态为 `已停`
- **THEN** 不创建 `tasks/`，不改代码

#### Scenario: 交接不等于完成

- **WHEN** task-explore 已进入 `handed-off`，driver 的 `tasks.md` 仍有未勾项
- **THEN** Goal 状态为 `已交接`
- **THEN** 不把 goal 标成完成

#### Scenario: driver 做完且判据成立

- **WHEN** driver checkbox 全勾，且 Goal 方案里的完成判据成立
- **THEN** 状态改为 `已完成`，对照判据说明，能标完成则标完成

#### Scenario: checkbox 全勾但判据不成立

- **WHEN** driver checkbox 全勾，但完成判据不成立
- **THEN** 状态改为 `已停`，不标完成

### Requirement: 审阅者先于开工
写完 Goal 方案、改代码之前，系统 MUST 叫一次审阅者。状态为 `执行中` 且出现新的决策点时 MUST 再叫。执行者写不出方案时 MUST 直接退出点「理解不够」，MUST NOT 叫审阅者。方案里已有线上动作、泄密或未点名的危险操作时 MUST 直接 `已停`，MUST NOT 叫审阅者。审阅者 MUST 只读。

出方案时，完成判据 MUST 保持一条可检查的话，「不做的事」MUST 列出本任务排除的行为。这两处是审阅边界。派审提示词 MUST 原样贴上当前完成判据、「不做的事」，以及该环节的审与不审。再审还 MUST 附上上一轮每一条 P0 与 P1，并要求逐条标已消失或仍在。提示词 MUST NOT 只写「范围同前」。再审 MUST 只核对这些 P0 与 P1，以及本轮写入直接造成、且仍落在该边界内的新 P0 或 P1。换一种写法仍指同一条判据、同一步或同一退出的，算仍在。

要新增完成判据与「不做的事」都没有的行为的意见，不编号，MUST NOT 写入方案，MUST NOT 参与完成程度。改完成判据只为让同一结果变得可检查。前提中的事实写错，且因此使现有步骤走不到这条判据时，该意见是 P0 或 P1。

- 步骤确定（写完方案到进入「写完之后」之前的初审）：审这条完成判据能否检查，按现有步骤能否走到它，以及阻塞点、退出点是否会改道。两行以内、要点与验证的写法、顺序、以及不改道的省略，编为 P2。不审架构、接口、schema、代码骨架，也不审边界外的新行为。P0 与 P1 只改这条判据的可检查写法，或步骤的动作、要点、验证。
- 执行中的新决策点：初审只审这一条岔路，以及它会改到的、尚未验证的步骤。不审已验证步骤、这条岔路碰不到的判据、详细设计。
- 已交接后的新决策点：初审只审尚未开始的步骤和这一条岔路。不审已交给下游的步骤、下游账本里已勾掉的实现、详细设计。还有未核对的 P0 或 P1 时，只写入并核对尚未开始的步骤，MUST NOT 因完成程度把状态改回 `已停`。

只给范围内的意见编 P0、P1 或 P2。范围外的意见 MUST NOT 写入方案，也 MUST NOT 参与完成程度。半屏里没写到的仓库细节，只有会让步骤走错或让判据不可检查时才编为 P0 或 P1。意见写「需要详细设计」时不编号、不给设计内容；系统 MUST 改为 `已停`，路由标明本流程不做详细设计。

一次审阅 MUST 返回完成程度（高、中、低）和范围内的改进意见。每条意见 MUST 带 P0、P1 或 P2，写清改哪一条完成判据或步骤，并指回已有知识、已有方案或公开方案。完成程度 MUST 写入方案的「方案置信度」。P0 是完成判据不可检查，或按步骤走不到判据，或漏了会改道的阻塞或退出。P1 是验证对不住判据。本轮有 P0 或 P1 时，完成程度 MUST 取中或低。P2 是不改道的写法、顺序、两行限制或省略，MUST NOT 参与完成程度。本轮没有 P0 与 P1 时，完成程度 MUST 为高；审阅者给了中或低时，执行者按高写入。审阅者把完成程度判为高且本轮仍有 P0 或 P1 时，系统 MUST 视为未通过，完成程度按中写入。

默认审阅者 MUST 是当前宿主拉起的子 agent，优先更强模型；当前已是最强档时 MUST 另起一个同模型子 agent，并在方案里记「无更强档」。起不来 MUST 换下一个可用模型，最多两次；两次都没有审阅结论时 MUST `已停`，退出点「审阅没有结论」。执行者自己给出的完成程度 MUST NOT 算审阅结论。

goal 原文或当轮用户消息写了 `agent-roster` 时，系统 MUST 委托 `$agent-roster` 做名册审阅。点名了唯一 Endpoint 时 MUST 走其快速路径。只说用名册、没点名谁时，MUST 按 routing 选一个最匹配的直接派，MUST NOT 列出候选表等人圈选。执行器不可用、证据不足或还要人时，MUST `已停`，退出点「审阅派不出」，MUST NOT 改回本机子 agent。

评审是否通过只看完成程度是否为高。只有完成程度、没有改进意见、也没有诚实结论时，系统 MUST 再叫一次审阅者；第二次仍没有则 MUST `已停`，退出点「审阅没有结论」。

评审收敛 MUST 同时满足：完成程度为高，本轮没有未消失的 P0 与 P1。P2 MUST 只写入坑，MUST NOT 改步骤正文；写入后 MUST NOT 再审。收敛后 MUST 再次核对退出点，再进入档位路由。

初审有 P0 或 P1 时，系统 MUST 把它们写入完成判据或步骤，P2 写入坑，路由以「完善中」开头，状态保持 `执行中`，然后做第一次核对。写入完成判据时 MUST 仍是同一结果的一条可检查的话。此阶段 MUST NOT 改代码，MUST NOT 因完成程度 `已停`，MUST NOT 向用户索取「仍按此方案执行」或「按审阅建议改方案」。原判据不可检查、且意见给出仍描述同一结果的可检查句子时，MUST 用该句子替换判据。两条意见冲突时，采纳能让这条判据可检查的那条，另一条写入坑。

第一次核对里，上轮 P0 与 P1 全部已消失，且没有本轮写入直接造成的新 P0 或 P1：完成程度为高，收敛。某一条仍在：MUST `已停`，退出点「审阅不通过」，MUST NOT 再写入。上轮条目已消失，且新的 P0 或 P1 点名了本轮改动的那一句，以及它让哪条判据或退出失效：把这些新意见再写入一次，然后做第二次核对。点不出改动句或失效判据的新意见，MUST NOT 当作新的 P0 或 P1。

第二次核对里，这些新意见全部已消失，且没有又冒出的 P0 或 P1：完成程度为高，收敛。仍有未消失的 P0 或 P1，或又冒出新的 P0 或 P1：MUST `已停`，退出点「审阅不通过」，MUST NOT 第三次写入。

完成程度为中或低、且还有没核过的 P0 或 P1 时，系统 MUST 继续完善。核过仍在才使用「审阅不通过」。只剩 P2 MUST NOT 构成这个结论。范围内的 P0 或 P1 写不出改法时，系统 MUST `已停`，退出点「审阅不通过」，回复 MUST 写明要达到的完成程度以及已有知识、已有方案、公开方案为什么补不上。简单和中等 MUST NOT 把每一轮审阅都做成外部参照；缺口可能被公开做法补上且还没对照过公开方案时，MUST 先对照再下「写不出改法」的结论。

用户在完善期间明确说「仍按此方案执行」时，系统 MUST 停完善，并按当前已写下的步骤进入档位路由。系统 MUST NOT 主动索取这句。进入档位路由之后，简单档 MUST 改为 `执行中` 并继续；中等档 MUST 改为 `已交接` 并按中等路由开工；复杂档 MUST 保持 `已停`，直到用户说走 task-explore。

读到因审阅档位为中或低而 `已停` 的旧方案时，系统 MUST 不再等待授权，把当时未写入的建议写入方案，改为完善后再审。读到以「已达到预期」作为开工门的方案时，已写入的改进意见视为 P2 已完成；方案置信度为高且没有未写入的 P0 或 P1 时 MUST 按评审收敛进入档位路由，否则改为完善后再审并补上优先级。

#### Scenario: 只有 P2 且完成程度为高则收敛

- **WHEN** 初审没有 P0 与 P1，只有 P2
- **THEN** 完成程度为高，P2 已写入坑，步骤正文不变
- **THEN** 核对退出点之后按档位继续
- **THEN** 不再审

#### Scenario: 有 P0 或 P1 则再审

- **WHEN** 初审范围内有 P0 或 P1
- **THEN** 完成程度不是高；审阅者给了高时按中写入
- **THEN** P0 与 P1 写入完成判据或步骤，P2 写入坑
- **THEN** 路由以「完善中」开头，接着核对这些 P0 与 P1
- **THEN** 不改代码

#### Scenario: 第一次核对原意见已消失

- **WHEN** 第一次核对把上轮每条 P0 与 P1 标为已消失，且没有点名本轮改动句与失效判据的新 P0 或 P1
- **THEN** 完成程度为高
- **THEN** 不再审

#### Scenario: 同一缺口仍在但还能改

- **WHEN** 第一次核对中，上轮某一条 P0 或 P1 仍在，含只换了写法
- **THEN** 状态为 `已停`，退出点为「审阅不通过」
- **THEN** 不再写入。还能指出改法也不再开一轮

#### Scenario: 写入引起的新意见再核一次

- **WHEN** 第一次核对中上轮 P0 与 P1 已消失，且新的 P0 或 P1 点名了本轮改动的那一句以及失效的判据或退出
- **THEN** 这些新意见再写入一次并做第二次核对
- **THEN** 不改代码

#### Scenario: 第二次核对仍有 P0 或 P1

- **WHEN** 第二次核对中仍有未消失的 P0 或 P1，或又冒出新的 P0 或 P1
- **THEN** 状态为 `已停`，退出点为「审阅不通过」
- **THEN** 不再写入

#### Scenario: 派审只写范围同前

- **WHEN** 再审任务没有贴上当前完成判据与「不做的事」，只写范围与上一轮相同
- **THEN** 该次派审不合规，MUST 改写提示词后才算一次审阅

#### Scenario: 边界外的新行为不写入

- **WHEN** 审阅者要求把完成判据与「不做的事」都没有的行为加进完成判据或步骤
- **THEN** 该意见不编号，不写入方案，不参与完成程度

#### Scenario: 错误事实挡住现有判据

- **WHEN** 前提中的事实与已核对的环境不符，且因此使现有步骤走不到当前完成判据
- **THEN** 该意见是 P0 或 P1，写入前提或对应步骤

#### Scenario: 不改道的仓库细节不升为 P0 或 P1

- **WHEN** 审阅者指出半屏未写的仓库细节，且该细节不让步骤走错、也不让判据不可检查
- **THEN** 该意见不编为 P0 或 P1，不参与完成程度

#### Scenario: 步骤确定不接受详细设计

- **WHEN** 环节是步骤确定，且审阅者要求定接口、架构或代码骨架
- **THEN** 该意见不写入方案，不参与完成程度
- **THEN** 意见为「需要详细设计」时，状态为 `已停`，路由标明本流程不做详细设计

#### Scenario: 无法把完成程度做到高时诚实停

- **WHEN** 范围内的 P0 或 P1 写不出改法，且已对照已有知识、已有方案、公开方案
- **THEN** 状态为 `已停`，退出点为「审阅不通过」
- **THEN** 回复写明要达到的完成程度，以及这三处为什么补不上

#### Scenario: 旧的中低停住改为完善

- **WHEN** 读到因审阅档位为中或低而 `已停` 的方案，且建议当时没有写入步骤
- **THEN** 不再等待授权
- **THEN** 把那些建议写入方案并再审

#### Scenario: 名册派不出

- **WHEN** goal 原文写了 `agent-roster`，且名册执行器不可用
- **THEN** 状态为 `已停`，退出点为「审阅派不出」
- **THEN** 不改用本机子 agent
